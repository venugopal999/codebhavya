⚙️ 15. Preprocessor & Header Files

🎓 Concept-First Explanation

This lesson is organized in the same order a faculty member would normally teach it: meaning → purpose → syntax/model → internal working → examples → common confusion → safe use. The guided examples from the earlier lesson are preserved afterward for reinforcement.

15.1 Where the Preprocessor Fits

Preprocessing occurs before the compiler analyzes the resulting translation unit as C. Directives begin with # after optional leading whitespace and control inclusion, macros and conditional source selection.

source file + headers
      ↓ preprocessor
#include expansion / macro replacement / conditional selection
      ↓
preprocessed translation unit
      ↓ compiler

15.2 #include — Bring Header Contents into the Translation Unit

#include <stdio.h>
#include "my_math.h"

Conceptually, inclusion makes the selected header’s preprocessing tokens available at that point. Angle brackets and quotes use different implementation-defined search procedures; quotes generally give an opportunity to find a project/user header before system-style search.

15.3 What Belongs in a Header

  • Function declarations/prototypes intended to be shared.
  • Type declarations used by multiple source files.
  • Macro definitions intended as part of the interface.
  • extern declarations of shared objects when appropriate.
  • Small static inline functions when intentionally header-defined.
Usually avoid

Ordinary external object/function definitions in a header can create multiple-definition problems when included by several translation units, unless the design intentionally uses forms with suitable linkage.

15.4 Object-Like Macros

#define BUFFER_SIZE 256
#define PI 3.141592653589793

A macro name is replaced during preprocessing according to macro replacement rules. A macro constant is not a typed C object.

15.5 Function-Like Macros

#define SQUARE(x) ((x) * (x))

Parenthesizing parameters and the whole replacement expression protects against many precedence surprises, but it does not fix repeated evaluation.

int i = 3;
int y = SQUARE(i++); /* dangerous: argument appears twice */
Why macro side effects are dangerous

Macro arguments are token sequences substituted where the parameter occurs. If the replacement uses a parameter twice, an argument with ++, a function call or another side effect may be evaluated twice after compilation.

15.6 #undef

#define DEBUG 1
#undef DEBUG

#undef removes a macro definition from that point onward in preprocessing.

15.7 Conditional Compilation

#if defined(DEBUG)
    fprintf(stderr, "x=%d\n", x);
#endif

Conditional preprocessing decides which source tokens exist in the translation unit. This is different from runtime if: code excluded by preprocessing is not compiled as part of that branch.

15.8 #if, #ifdef, #ifndef, #elif and #else

DirectivePurpose
#iftest integer constant preprocessing expression
#ifdef NAMEtest whether macro NAME is defined
#ifndef NAMEtest whether macro NAME is not defined
#elifadditional preprocessing condition
#elsefallback branch
#endifclose conditional group

15.9 Include Guards

#ifndef CODEBHAVYA_MATH_H
#define CODEBHAVYA_MATH_H

int add(int a, int b);

#endif

A guard prevents the header body from being processed more than once within the same translation unit. It does not mean the header is included only once across the entire final program.

15.10 Predefined Macros

printf("File: %s\n", __FILE__);
printf("Line: %d\n", __LINE__);
printf("Built: %s %s\n", __DATE__, __TIME__);

Predefined macros can support diagnostics and build information. Avoid depending on build date/time when reproducible builds matter.

15.11 #pragma and Portability

#pragma provides implementation-defined control. A compiler may support pragmas for warnings, packing or optimization, but portable code should isolate and document compiler-specific pragmas.

15.12 assert Is Not the Same as Input Validation

#include <assert.h>
assert(index < length);

assert is intended for programmer assumptions/invariants and can be disabled when NDEBUG is defined. Do not rely on an assertion to validate untrusted user input or perform required runtime error handling.

15.13 Macro vs const vs enum vs static inline

ToolBest suited to
Object-like macropreprocessing/configuration/token substitution
const objecttyped read-only program object
enum constantnamed integral constants/states
static inline functiontyped reusable expression/operation without macro repeated-evaluation problems

15.14 Preprocessor Checklist

  • Does every header have a guard or equivalent supported mechanism?
  • Are macro parameters parenthesized?
  • Can a macro argument be evaluated more than once?
  • Is a typed constant/function clearer than a macro?
  • Is compiler-specific behavior isolated and documented?
  • Does conditional compilation test a capability rather than unnecessarily hard-coding a platform name?

What is the C Preprocessor?

The C preprocessor is a program that processes source code before the actual compilation begins.

Preprocessor directives begin with the # symbol. 

#include <stdio.h>
#define PI 3.14159

#include

The #include directive tells the preprocessor to include the contents of another file. 

#include <stdio.h>

This allows us to use functions such as printf() and scanf().

System Header Files

Standard C libraries provide commonly used functions through header files. 

#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <math.h>
Header Examples

math.h sqrt(), pow(), sin()
ctype.h isdigit(), isalpha(), toupper()
time.h time(), clock()

<> vs " " in #include

There are two common forms of the include directive. 

#include <stdio.h>

#include "myheader.h"
Syntax Typical Use
#include <file.h> System / standard headers
#include "file.h" Project / local headers

#define

The #define directive creates a macro. 

#define PI 3.14159

Wherever the macro name appears later in the source, the preprocessor substitutes its replacement text. 

#include <stdio.h>

#define PI 3.14159

int main()
{
    printf("%f", PI);

    return 0;
}

Object-like Macro

#define MAX 100

#define MIN 0

#define COLLEGE "ABC College"

These are called object-like macros because they do not take arguments.

Macro with Expression

#define PI 3.14159

#define LIMIT 50

#define SIZE 10
💡 A macro is handled by the preprocessor before compilation. It is not a typed variable.

Function-like Macro

A macro can accept arguments. 

#define SQUARE(x) ((x) * (x))
printf("%d", SQUARE(5));
25

Why Parentheses Matter in Macros

Always use parentheses carefully when writing expression macros.

Prefer: 

#define SQUARE(x) ((x) * (x))

instead of: 

#define SQUARE(x) x * x

The parenthesized version avoids many operator precedence problems when the macro is used inside larger expressions.

Macro with Multiple Arguments

#define MAX(a, b) ((a) > (b) ? (a) : (b))
printf("%d", MAX(10, 20));
20

Macro vs Function

Macro Function
Processed by preprocessor Compiled as a function
No normal type checking for arguments Arguments have declared types
Text substitution Function call
Can cause repeated evaluation of arguments Arguments are evaluated according to function-call rules

Macro Side Effects

Be careful when passing expressions with side effects to function-like macros. 

#define SQUARE(x) ((x) * (x))

int i = 5;

int result = SQUARE(i++);

This is dangerous because the argument may be expanded more than once.

⚠️ Prefer functions when you need predictable argument evaluation and type checking.

#undef

The #undef directive removes a previously defined macro. 

#define SIZE 100

#undef SIZE

Conditional Compilation

Conditional compilation allows parts of the source code to be included or excluded depending on preprocessor conditions. 

#if condition

    /* code */

#endif

#if

#define VERSION 2

#if VERSION == 2

printf("Version 2");

#endif

The code between #if and #endif is included only when the condition evaluates as true.

#if and #else

#define DEBUG 0

#if DEBUG

printf("Debug mode");

#else

printf("Normal mode");

#endif
Normal mode

#elif

#define VERSION 2

#if VERSION == 1

printf("Version 1");

#elif VERSION == 2

printf("Version 2");

#else

printf("Other version");

#endif

#ifdef

#ifdef checks whether a macro is defined. 

#define DEBUG

#ifdef DEBUG

printf("Debug mode enabled");

#endif

#ifndef

#ifndef checks whether a macro is not defined. 

#ifndef DEBUG

printf("DEBUG is not defined");

#endif

Header Guards

Header guards prevent the same header file from being included multiple times in a single compilation unit. 

#ifndef STUDENT_H
#define STUDENT_H

struct Student
{
    int roll;
    char name[50];
};

#endif
🎯 Header guards are commonly written using #ifndef, #define, and #endif.

Creating Your Own Header File

We can create our own header file containing declarations and reusable code.

Example file: 

mathutils.h

Content: 

#ifndef MATHUTILS_H
#define MATHUTILS_H

int add(int a, int b);
int subtract(int a, int b);

#endif

Using a User-defined Header

Create a source file containing the function definitions. 

#include "mathutils.h"

int add(int a, int b)
{
    return a + b;
}

int subtract(int a, int b)
{
    return a - b;
}

Including Your Header in main()

#include <stdio.h>
#include "mathutils.h"

int main()
{
    printf("%d\n", add(10, 20));

    printf("%d\n", subtract(20, 10));

    return 0;
}

#pragma

#pragma provides implementation-specific instructions to the compiler.

Its exact behavior depends on the compiler and platform. 

#pragma once

Many compilers support #pragma once as a way to prevent multiple inclusion of a header.

⚠️ #pragma directives are generally compiler-specific. Prefer portable techniques such as traditional include guards when portability is important.

Predefined Macros

C implementations provide several predefined macros. 

#include <stdio.h>

int main()
{
    printf("File: %s\n", __FILE__);

    printf("Line: %d\n", __LINE__);

    printf("Date: %s\n", __DATE__);

    printf("Time: %s\n", __TIME__);

    return 0;
}

Common predefined macros include:

  • __FILE__ → current source file name
  • __LINE__ → current line number
  • __DATE__ → compilation date
  • __TIME__ → compilation time

assert.h

The assert.h header provides the assert() macro for debugging checks. 

#include <assert.h>

int x = 10;

assert(x > 0);

If the expression is false, the assertion normally reports a diagnostic and terminates the program.

🔍 Deeper understanding: Macros are token substitution, not functions

The preprocessor works before C type checking. A function-like macro can evaluate an argument more than once and can group incorrectly unless both parameters and the entire replacement expression are parenthesized. Even a parenthesized macro cannot make side-effect arguments safe.

#define SQUARE_BAD(x) x * x
#define SQUARE(x) ((x) * (x))

/* SQUARE(i++) is still unsafe because i++ appears twice. */

Include guards prevent repeated declarations within one translation unit:

#ifndef CODEBHAVYA_MATH_H
#define CODEBHAVYA_MATH_H
/* declarations */
#endif

#if controls which tokens are compiled; an ordinary if is part of the compiled program and is evaluated while it runs. Prefer typed const objects or inline functions when textual substitution is unnecessary.

Common Preprocessor Mistakes

  • Forgetting the # before a directive.
  • Writing a function-like macro without careful parentheses.
  • Passing expressions with side effects to macros.
  • Including the wrong header file.
  • Forgetting header guards.
  • Assuming #pragma behavior is portable.
  • Using macros when a normal function would be clearer and safer.
Reasoning trace:
SQUARE(i++) → ((i++) * (i++)) → duplicated unsequenced modification → undefined behaviour
📘 Standard and portability note

Macros are preprocessing token substitution. Prefer inline functions when type checking and single evaluation are required.

✓Why is SQUARE(i++) unsafe when SQUARE expands to ((x) * (x))?
Correct Answer: B

Parenthesizing fixes grouping problems but cannot prevent repeated evaluation.

🧠 Deep Dive — What Really Happens Before Compilation

The Preprocessor Does Not Understand C Types

The preprocessor works with preprocessing tokens and directives before normal compilation performs type checking. That is why a macro can produce invalid C even though the macro definition itself looked reasonable.

#define TWICE(x) ((x) + (x))

TWICE(3)       /* becomes ((3) + (3)) */
TWICE("abc")   /* substitution happens too; later compilation rejects the expression */

The macro system performs textual/token-oriented transformation. It is not a typed function system.

#include Conceptually Inserts Header Content

#include <stdio.h>
#include "my_math.h"

Both directives request inclusion of a header, but the implementation uses different search rules for the angle-bracket and quoted forms. The exact search paths are implementation-defined. The important programming idea is that declarations from the header become available in the translation unit being compiled.

💡 Why do headers normally contain declarations rather than ordinary function definitions?

A header can be included in many source files. Placing a non-static ordinary function definition in such a header can create multiple external definitions at link time. Headers therefore usually expose declarations, type definitions, macros and carefully designed static inline helpers.

Include Guards Protect One Translation Unit from Repeated Inclusion

#ifndef CODEBHAVYA_ACCOUNT_H
#define CODEBHAVYA_ACCOUNT_H

struct Account;
void account_print(const struct Account *a);

#endif

The first inclusion defines the guard macro. Later attempts to include the same guarded header in that translation unit skip the guarded body. Include guards do not make an invalid set of declarations valid; they simply prevent accidental repeated processing.

Conditional Compilation Happens Before Runtime

#if DEBUG_LEVEL >= 2
    #define TRACE(msg) fprintf(stderr, "TRACE: %s\n", (msg))
#else
    #define TRACE(msg) ((void)0)
#endif

Only the selected branch contributes tokens to the later compilation stages. This is fundamentally different from:

if (debug_level >= 2) {
    /* runtime decision */
}

A normal if exists in the compiled program and is evaluated during execution. #if controls which source is compiled at all.

Undefined Names in #if

After macro replacement, identifiers that remain in a preprocessing conditional expression are treated as 0 for the expression. Even so, explicit feature checks are clearer:

#if defined(FEATURE_LOGGING) && FEATURE_LOGGING
    /* logging code */
#endif

#pragma Is Implementation-Oriented

#pragma provides implementation-specific control. A compiler may support directives for warnings, packing, optimization or other features, but those pragmas are not automatically portable to another implementation.

Common confusion: macro constant vs typed constant
#define LIMIT 100
const int limit = 100;

LIMIT is replaced by preprocessing tokens. limit is an actual typed object subject to C's scope and type rules. Choose the mechanism that matches the need rather than treating them as identical.

A Header's Responsibility

A reusable header should normally be self-contained: if another source file includes it directly, the declarations should still compile. Include what the header itself needs, use guards, keep private implementation details out, and avoid definitions that cause multiple-definition problems.

INTERVIEW PREPARATION

🎤 Preprocessor & Header Files — Interview Questions







1.
What happens before compilation when the C preprocessor runs?





                It handles preprocessing directives such as file inclusion, macro expansion, and conditional source selection before the compiler receives the resulting source.
            







2.
Why should macro parameters usually be wrapped in parentheses?





                Parentheses help preserve the intended grouping when the argument itself is an expression.
            







3.
What is a common danger of function-like macros?





                A macro argument can be evaluated more than once after expansion, so expressions with side effects such as i++ can behave unexpectedly.
            







4.
What is the difference between #ifdef and #ifndef?





                #ifdef keeps a block when a macro is defined; #ifndef keeps a block when that macro is not defined.
            







5.
What are header guards?





                They are conditional preprocessing directives, typically #ifndef, #define, and #endif, used to prevent repeated processing of the same header within one translation unit.
            







6.
What is the difference between #include <file.h> and #include "file.h"?





                They use different header-search forms. Angle brackets are commonly used for system headers, while quotes are commonly used for project headers.
            







7.
What does #undef do?





                #undef removes the current macro definition associated with a macro name.
            







8.
Why is #pragma considered less portable?





                #pragma is intended for implementation-specific control, so supported pragmas and their behavior can vary by compiler.
            









PLACEMENT TIPS

💡 Preprocessor & Header Files — Placement Tips


    

  • For function-like macros, parenthesize both each parameter and the entire replacement expression.
    • 

  • Avoid passing expressions with side effects such as i++ to macros that use the same parameter more than once.
    • 

  • Use header guards in reusable project headers to prevent repeated declarations caused by multiple inclusion paths.
    • 

  • Keep declarations and shared interfaces in header files; keep function definitions in source files unless there is a specific reason otherwise.
    • 

  • Use conditional compilation for build-time choices such as debugging code or platform-specific sections.
    • 

  • Remember that preprocessing happens before runtime, so #if cannot directly test a normal runtime variable.
    •
